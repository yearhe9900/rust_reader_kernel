# 分析-代码深审与架构评审（v0.4.0 / ABI 11）

> **基线**：`281970a`（v0.4.0，ABI 11），2026-11-06。
> **范围**：全 workspace 16 个 crate 的核心链路、`rrk-ffi` C ABI 面、Dart 封装、
> CI/Release 脚本、契约文档三件套（ROADMAP / FFI 调用约定 / CHANGELOG）。
> **方法**：按「数据从哪来 → 怎么变成统一模型 → 怎么过边界 → 怎么被缓存」的链路读，
> 而非按模块清单扫。每一条结论都带文件行号，可复现。
> **立场**：这份报告**不重复**外部那份「观后感」的功能清单。那份盯的是「还缺什么功能」，
> 本文盯的是**架构契约、ABI 演进成本、工程门禁与数据正确性**——即决定这个项目
> 三年后还好不好维护的东西。

---

## 一、总评

**架构评级：A-（骨架相当正，契约层开始出现结构性欠债）。**

分层的边界感是真的：`rrk-format` 只定义「格式 → 统一书源」，`rrk-model` 只放不可变数据，
`rrk-layout` 是纯函数，`rrk-kernel` 管生命周期与缓存，`rrk-ffi` 只做边界防御。
坐标系用 UTF-8 字节偏移一路贯穿锚点 / 内链 / 搜索命中 / 进度 / hit_test，
没有出现「页码派」与「字节派」两套真值打架——这一条绝大多数开源阅读内核都做不对。

扣分不在功能，在**两处结构性问题**：

1. **C ABI 的参数结构没有版本化机制**。`rrk_pages_json` / `page_at` / `hit_test` /
   `prefetch` 四个出口各把 9 个排版参数（`font_ptr`…`dpr`）原样列一遍，Dart 侧同样重复
   四遍。这意味着「加一个字间距」要同时改 4 个 C 签名 + 4 个 Dart 方法 + 重生成头文件，
   契约文档 §5 承诺的「符号与语义只增不改」被结构性架空。
   讽刺的是，同一个项目里 **RLAY 二进制 payload 有 `RLAY_SCHEMA` 号可以平滑演进**
   （`rrk-model/src/layout.rs:127`），C ABI 这层却没有等价物。
2. **`content_hash` 被当成内容身份用，但它不是**。它是前 1MB（EPUB 更极端：OPF 前 64KB）
   的 FNV-1a，而 v0.4.0 刚把它用作**磁盘持久化缓存的 key**。于是「改了正文」不再只是
   哈希不敏感，而是「重开命中旧索引、旧章文本，用户读到旧内容」——正确性缺陷。

其余大多是打磨项。下面按严重度排。

## 二、先说不要动的：这套代码做对的地方

评审若不写这一节，容易让人误以为该重写。以下几处是真踩过坑才有的设计，**不建议为了"整齐"去动**：

| 项 | 证据 | 为什么值得保留 |
|---|---|---|
| panic 不穿 ABI 的双保险 | `rrk-ffi/src/lib.rs:16`（clippy `deny`）+ CI `ci.yml:24` + 源码扫描测试 `every_ffi_export_is_guarded`；`guard`/`guard_val` 连 `rrk_abi_version` 这类常量出口也一刀切包（L192-196） | 门禁是机器可验证的，不是写在文档里的口号 |
| 锁中毒自恢复 + 句柄 generation + per-request 取消令牌 | `rrk-ffi/src/lib.rs:112-121`、L66-96、`CHANGELOG.md:95-110` | 一次被 2001 拦下的 panic 不会让引擎永久瘫痪；关 A 开 B 不会 ABA；布局 B 启动不会吞掉对 A 的取消 |
| **重活出锁** | `layout_pages_cached` L1416-1471 三段式；契约文档 §4 锁范围表逐项列明 | 载章/排版/落盘期间其它 FFI 调用（含 cancel）不被阻塞，这是 cancel 能生效的前提 |
| 缓存**载入前可信校验** | `CHANGELOG.md:45-48`；EPUB 对拍 spine href 序、CBZ 对拍条目存在性、PDF 对拍页对象 | 绝大多数项目是"解出来就用"，这里对持久化索引做了语义对拍，工程成熟度很高 |
| payload 自带 magic + schema + 纯函数排版 + 金样 | `rrk-model/src/layout.rs:126-127`；`rrk-layout/tests/golden_layout.rs`；`RRK_GOLDEN_BLESS=1` | 升级 parley 时 diff 就是排版真相变化，不是靠肉眼看截图 |
| fuzz 五目标 + 畸形输入加固 | `ci.yml:91-121`；`CHANGELOG.md:159-161`（230 字节 → 24GiB realloc 的实锤案例） | 有真实 OOM 案例驱动，不是摆设 |

另外，`set_last_error` 用 `thread_local`（`rrk-ffi/src/lib.rs:103-106`），契约文档 §2 明确
「必须同线程立刻读取」——多线程不串味，设计正确，无需改。

## 三、A 级：数据正确性（应该最先修）

### A1 · `content_hash` 不是内容身份，磁盘缓存把它放大成「读到旧内容」

**证据**

| 格式 | 计算方式 | 位置 |
|---|---|---|
| EPUB | `fnv1a64(&opf_xml[..min(64KB)])` —— **正文一个字节都不进哈希** | `rrk-epub/src/lib.rs:170` |
| PDF / CBZ / MOBI / TXT | 文件前 1MB | `rrk-pdf/src/lib.rs:115`、`rrk-cbz/src/lib.rs:226`、`rrk-mobi/src/lib.rs:424`、`rrk-txt/src/lib.rs:338` |

`CacheKey::content(content_hash, kind)` 同时驱动内容级缓存（目录/章文本/大纲）与
五格式 open 索引磁盘缓存（`rrk-epub/src/lib.rs:187`、`CHANGELOG.md:37-52`）。
于是一本 EPUB 只要 OPF 不变，改任意章节、重开 → 命中旧章文本与旧章表。
FNV-1a 是 64 位非加密哈希，作持久 key 也无冲突防护。

**这不是可以等"流式/mmap 改造"一起做的事**，成本极低：
`ZipEntry` 已经存了 `crc32`（`rrk-zip/src/lib.rs:86,109`），中央目录解析时就拿得到。
用「条目名 + crc32 + uncomp_size」有序列表做指纹是 **O(条目数)**，不读正文、不占内存。
非 zip 格式用「文件长度 + 头/中/尾三段采样」，或干脆流式全量哈希（顺序读，不驻留）。
同时建议把 `content_hash` 在文档里正名为**版本指纹**，明确"不保证内容相同性"。

### A2 · hit_test 会算出非法 UTF-8 边界

`run_offset_at`（`rrk-ffi/src/lib.rs:1540-1569`）按**字节**比例在 run 内插值：

```rust
let off = (ratio * len as f32) as u32;   // len = range.1 - range.0，UTF-8 字节数
best = (r.range.0 + off.min(len)).min(hit_range.1);
```

中文一个字符 3 字节，落点极易切在字符中间。宿主拿这个偏移去 `rrk_slice_text`
或做选区高亮，得到的不是"偏几个像素"，而是**非法 char boundary**。
v0.4.0 把硬编码 20px/字修成按 `TextRun.width` 插值是一次进步，但没解决粒度问题。

最小修复：插值结果向下/向上吸附到章文本的 char boundary（需要一个 `&ChapterContent.text`
入参，纯函数仍可测）。彻底修复：在 `TextRun` 里带 cluster 的 X 偏移数组
（parley 的 GlyphRun 本来就有 advance），RLAY schema 2 → 3，旧缓存自动丢弃重算——
schema 机制现成的，不用怕兼容。

### A3 · EPUB/MOBI 正文段落永远不缩进（用户每天看得见）

`Cleaner::flush` 恒写 `Block::Paragraph { indent: false }`（`rrk-markup/src/clean.rs:125`），
而 `StyleSpec::para_indent_em` 的文档明确「仅对 `indent: true` 生效」
（`rrk-model/src/layout.rs:32`）。结果只有 TXT（`rrk-txt/src/lib.rs:539-547` 靠行首全角空格猜）
和 PDF 重排（`rrk-pdf/src/lib.rs:292`）吃得到用户设置，EPUB/MOBI 一律无效。
默认值是 2em，也就是说**默认样式在主流格式上是摆设**。

根因见 C5：这不是 clean.rs 少写一个 `true` 的问题。

## 四、B 级：契约与架构演进成本

### B1 · `rrk_open` 只吃文件路径，真实移动端接入面被砍掉一半

`rrk_open(path_ptr, path_len)` 强制 UTF-8 路径字符串（`rrk-ffi/src/lib.rs:471-505`），
`ContentSource::Bytes`（`rrk-format/src/lib.rs:21-24`）**没有任何 FFI 出口**。
于是这些场景全部接不进来，宿主只能先把书落盘到一个可读路径：

- Android `content://` / SAF / 沙盒 URI（没有真实文件路径）；
- iOS security-scoped URL、iCloud Drive 按需下载；
- 网盘/HTTP 流式、DRM 之外的内容解密后内存字节；
- 想把书放在加密容器里、不让明文落盘的产品。

这比「大文件 OOM」更早卡住接入。建议分两步：
① 立刻加 `rrk_open_bytes(data, len, name)`（additive，ABI 只增）解接入；
② 把 `ContentSource::read_all`（L43-54）升级为带 `read_at(off, len)` 的 trait default，
   让 `ZipArchive` / `PdfDocument` 能只驻留中央目录与 xref，再谈 mmap。
顺序不能反：先改 IO 抽象会让所有 adapter 一次性重写，风险高、收益要先有真实大书样本。

> 顺带澄清一个常见混淆：**2GB CBZ 的痛点是 `std::fs::read` 全量入堆，不是 Zip64**。
> Zip64 门槛是 >4GB 或 >65535 条目（`rrk-zip/src/lib.rs:70-72,101-103`）。两件事别捆在一起估工。

### B2 · 排版参数重复四遍，加一个样式字段就要破一次 ABI

| 出口 | C 签名 | Dart 封装 |
|---|---|---|
| `rrk_pages_json` | `rrk-ffi/src/lib.rs:1475-1489` | `rrk_reader.dart:1006-1022` |
| `rrk_page_at` | L1504-1518 | L1037-1051 |
| `rrk_hit_test` | L1574-1590 | L1157-1172 |
| `rrk_prefetch` | L1659-1674 | L1184-1200 |

四处全是 `font_ptr, font_len, font_size, line_height, para_indent_em, align, width, height, dpr`。
新增 `letter_spacing` / `paragraph_spacing` / 竖排 / 主题色，全部要同步改 8 处 + 头文件 +
所有宿主调用点。`CHANGELOG.md:204` 已经承认 v0.2.0 有「两轮破坏性变更」，
说明这条演进路径已经在付代价了。

对比 `rrk-model/src/layout.rs:127` 的 `RLAY_SCHEMA`：**数据面有版本化，边界没有**。
建议（推荐前者）：

- 引入不透明 `StyleHandle` / `ViewportHandle`：`rrk_style_create(...)` 返回句柄，
  四个出口改成只接句柄；以后加字段是「新增 setter」，签名不动；
- 或退一步，把参数打包成带 `version` + `size` 的结构体指针，
  一次性破 ABI，之后靠 `size` 前向兼容扩展。

契约文档 §5 也应把措辞从「符号与语义只增不改」改成可验证的
「**同一 ABI 号内不破坏；bump 时宿主与原生库必须同步升级**」——
毕竟 `RrkEngine.init` 是**相等校验、不匹配直接 throw**（`rrk_reader.dart:280-282`），
没有灰度窗口，这是真实的部署约束，应该写进契约而不是藏在代码里。

### B3 · ABI 常量三处硬编码，靠运行时兜底，CI 没有一致性门禁

`RRK_ABI_VERSION = 11`（`rrk-ffi/src/lib.rs:47`）、`kRrkAbiVersion = 11`
（`rrk_reader.dart:20`）、CHANGELOG 里的版本号，三处人工同步。
提交 `d40f59f` 的标题就是「同步 ABI 常量到 v11」——**已经漏过一次**。
CI 已经有 `cbindgen --verify` 头文件漂移校验（`ci.yml:34`），却没有一个 10 行脚本
对比 Rust 常量 / Dart 常量 / `bindings/rrk.h` / CHANGELOG。这个缺口补起来几乎零成本，
建议在 `cargo test --workspace` 之前加一步。

### B4 · open 索引缓存的开关被绑到了内容级缓存上

`Kernel::open_index_cache()` 返回 `self.content_cache.as_ref().map(|(s, _)| s.clone())`
（`rrk-kernel/src/lib.rs:517-519`），`OpenIndexStore` 持 `Option<DiskStore>`（L49-52）。
而 `rrk_open` 无条件走它（`rrk-ffi/src/lib.rs:487-491`）。后果：

- 宿主只想关掉内容级缓存（省空间），**连 open 索引缓存也一起没了**；
- 只想开 open 索引缓存、不想缓存章文本，**做不到**；
- FFI 没有独立的配置出口，文档也没说明这层耦合。

两者实现于不同批次（issue #12 vs ROADMAP 扩展），属于典型的「复用了现成 store，
顺手把生命周期也绑上了」。建议给 open 索引一个独立 `IndexCache` 句柄与配置面，
或至少在契约文档里把开关语义写清楚。

### B5 · C2 磁盘缓存没有容量上限

C1 内存层有 LRU + 保护窗口（`rrk-cache/src/lib.rs:182-185`），
`DiskStore`（L230-290）只有 `open/save/load/invalidate`，**没有 evict / trim / 配额**。
布局缓存 key = `content_hash × style_hash × viewport_hash`（三要素），
用户每改一次字号、旋转一次屏幕、换一台设备，就是一批新文件，永不清理。
移动端磁盘配额是硬约束。ROADMAP L25 说「落盘/缓存策略归宿主」，
那就至少该给宿主一个 `rrk_cache_trim(max_bytes)` / 配置时带 `disk_bytes` 上限，
否则"归宿主"无从执行。

## 五、C 级：工程一致性与保真度

- **C1 · unwrap 门禁只覆盖一个 crate**。生产代码仍有 13 处 `.lock().unwrap()`
  （`rrk-format/src/lib.rs:147,156`；`rrk-pdf/src/{lib.rs:211,225, objects.rs:730,733,752,782,824, raster.rs:108,181,975,1004}`），
  而 `deny(clippy::unwrap_used)` 只在 `rrk-ffi`（`ci.yml:24` 也是 `-p rrk-ffi`）。
  风险实际很低（都是内部缓存锁），但**门禁口径不一致**会让后来者误判红线范围。
  建议全 workspace 统一 `lock_recover`，或明确写「红线仅适用于 FFI 出口」。
- **C2 · `rrk_buf_free(ptr, len)` 要宿主回传 len**。`alloc_buf` 用 `Box<[u8]>`，
  释放时靠 `slice_from_raw_parts_mut(ptr, len)` 重建（`rrk-ffi/src/lib.rs:167-189`），
  len 传错即 UB，内核无法防御。契约文档 §1 已写明，所以**不是 bug**，
  但设计上应让内核自记长度（ptr 前置 header 或分配表），把 `len` 降级为可选参数。
- **C3 · 排版器池按调用次数轮转，不是按空闲槽**。
  `&pool[RR.fetch_add(1) % pool.len()]`（`rrk-ffi/src/lib.rs:64`），
  而整章排版是**持槽锁跑完**的（`layout_pages_cached` L1457-1461）。
  两个请求落到同槽仍串行，契约文档 L44「吞吐随池叠加」在冲突时打折。
  改成 `try_lock` 先找空闲槽、全忙再排队，几乎不改动调用面。
- **C4 · CI 语料全是合成小样本**。`ci.yml:26,80` 的冒烟与 bench 都用
  `fixtures/sample.txt`，`fixtures/` 共 4 个小文件；fuzz 覆盖畸形输入、
  金样覆盖排版，但**没有真实书端到端回归**。而本地实测过 7.1MB / 1152 章 EPUB、
  24MB MOBI/AZW3、301 页 PDF——这些复杂度没进 CI。
  建议加一份公开领域语料清单（路径 + sha256），CI 跑 `open → toc → 抽样 load_chapter
  → 偏移/内链对拍`，哪怕只 3 本，也能挡住"索引重建逻辑改坏"这类回归。
- **C5 · 缩进是解析层决策，不是样式层决策（A3 的根因）**。
  `Block::Paragraph { indent: bool }`（`rrk-model/src/lib.rs:219`）把「是否缩进」
  这个**呈现决策**压进了格式解析。于是 TXT 靠行首全角空格猜、EPUB 恒 false、
  PDF 靠前缀猜，三套启发式互不统一，而用户在 `StyleSpec` 里设的 2em 管不着它们。
  正解是块带**语义角色**（`body / first-of-section / quote / verse / pre`），
  由排版层按角色 + 样式决定是否缩进。这样 A3 自动消失，也让 C6 的 `pre` 保真有落点。
- **C6 · 模型变体与消费方脱节**。`Inline::Image` 在模型里存在
  （`rrk-model/src/lib.rs:206`），清洗层 `<img>` 却无条件 flush 成 `Block::Image`
  （`rrk-markup/src/clean.rs:195-220`），`Layouter::layout_inlines` 又只匹配 `Inline::Text`
  （`rrk-layout/src/lib.rs:151-158`）。同类：`pre/table/blockquote/li` 全拍平（clean.rs:226-229）、
  `<pre>` 换行被 `collapse_ws` 压成一行、ruby 注音直接丢弃（L182-188）。
  功能缺口外部 review 已列全，这里只强调**工程含义**：模型声明了变体却没有
  「消费方必须穷举」的编译期或测试约束，将来加 `Inline::Ruby` / `Inline::Code`
  还会静默丢。建议加一个 `match` 穷举 + 单测钉住每个变体至少被一条管线消费。

## 六、明确不作为问题提出（含对上一轮判断的自我修正）

评审的价值一半在于**不误报**。以下几点核实后不成立或口径需校正：

1. **「内核内落盘」红线没有被破坏**。我上一轮说 ROADMAP L25「永久不做」与
   v0.4.0「自动走 C2 磁盘层」自相矛盾，**这个判断过重了**。
   `rrk_cache_configure` / `rrk_content_cache_configure` 都要求宿主显式传目录
   （`rrk-ffi/src/lib.rs:1156-1160`，空路径 = `None`），`OpenIndexStore.store` 是
   `Option<DiskStore>` 且 `load` 首行 `let store = self.store.as_ref()?`
   （`rrk-kernel/src/lib.rs:80`）。**未配置即不落盘**，红线成立。
   真正的问题是**表述歧义**：CHANGELOG 写「open 自动走 C2 磁盘层」容易被读成默认落盘，
   建议改文案，不是改代码。
2. **ROADMAP 标题滞后**：L6 仍写「已落地（截至 v0.1.x / ABI 8）」，
   而当前是 v0.4.0 / ABI 11，且 L32-39 的待办已全部 ✅。属文档维护，非架构问题。
3. **iOS/XCFramework 不是"新需求"，是已承诺未兑现**。总体方案 §427/§539 写明
   `ios/Frameworks/rrk.xcframework` 随包，而 `scripts/package-release.sh:187-188`
   明确「本包不含 iOS 产物」，CI 仅 Linux/macOS/Windows（`ci.yml:132`）。
   应记为欠债，不该当成扩展受众的加分项。
4. **`system_font_path` 的 Linux 分支也是摆设**：`rrk-pdf/src/raster.rs:80` 在
   `/usr/share/fonts` 下找 `arial.ttf` / `times.ttf`，真实发行版里没有这些文件
   （且在子目录中）。所以缺口不止 macOS/Android/iOS，Linux 也未真正覆盖。
5. **wasm 不在本项目范围**，全仓零匹配，不评价、不进待办。
6. **MOBI 大书现在是明确报错而非静默 OOM**：`MAX_TEXT_BYTES = 256MB`
   （`rrk-mobi/src/lib.rs:36`）、单次 unpack 预算、PDF `MAX_PIXMAP_PIXELS = 1e8`
   （`raster.rs:315`）。外部 review 描述的"OOM"是加固前状态。

## 七、建议路线（按「改动量 × 收益」排序，非按模块）

| 序 | 项 | 改动面 | 收益 | 备注 |
|---|---|---|---|---|
| 1 | A1 内容版本指纹 | 5 个 adapter 各几行 + 文档 | **消除读到旧内容的正确性缺陷** | zip 用现成 `crc32`，不必等流式改造 |
| 2 | A3 + C5 段落语义角色 | `rrk-model` + `clean.rs` + layout | 默认样式在 EPUB/MOBI 真正生效，用户每天可见 | 建议一起做，别只把 `false` 改 `true` |
| 3 | B3 CI 的 ABI 常量校验 | 一个脚本 + workflow 一步 | 消除已发生过的人肉漏同步 | 10 行成本 |
| 4 | A2 hit_test 吸附 char boundary | `rrk-ffi` 纯函数 + 单测 | 选区/查词不再返回非法偏移 | cluster 数组可放第二步 |
| 5 | B1 `rrk_open_bytes` | 新 FFI 出口 + Dart 方法 | 解锁 Android SAF / iOS 沙盒 / 内存字节 | additive，不动既有 ABI |
| 6 | B4 / B5 缓存开关与配额 | kernel + cache + 2 个出口 | 移动端磁盘可控 | 可与 B1 同批 |
| 7 | C1 / C2 / C3 一致性收口 | 全局替换 + 2 个契约微调 | 红线口径统一、消除 UB 可能 | 低风险，适合穿插做 |

## 八、一句话结论

**这套内核的"数据面"已经是生产级（坐标统一、纯函数排版、带 schema 的缓存、
机器可验证的 panic 门禁），真正欠债的是"边界"**：C ABI 没有版本化参数结构、
`content_hash` 承担了它承担不起的身份语义、开书入口只认文件路径。
这三件事都不需要重写，但越晚改，宿主越多、改起来越疼。

功能层面那些"行内图 / 代码块 / ruby / 缩进 / 字体注入"是打磨，不是架构问题——
按 A3 → C6 的顺序顺手收掉即可，别让它们挤掉前三项的排期。
