一全景：五个层各管什么

整个系统的核心原则是计算面与呈现面分离：解析、解压、排版、缓存这些重活全在 Rust 内核（无 GC、可并行、产物可落盘）；Flutter 只做合成、手势与动画。两层之间靠 FFI 批量传递数据，一次调用 = 一个完整任务。

二解析：EPUB 与 TXT 如何变成同一种数据

两种格式走完全不同的解析路径，但出口是同一个 —— 统一数据模型的 Block 流。这就是「解析与渲染职责分离」的落点：排版层只认 Block，完全不感知背后是 EPUB 还是 TXT。

图 2 · 双路径解析，单一出口：无论什么格式，排版层拿到的都是干净的 Block 流

EPUB 解析细节

  • zip 随机读：只读一次中央目录拿到全部条目表，绝不整包解压；每章按需 inflate 单个条目。
  • OPF 三件套：metadata（书名/作者/封面）→ manifest（条目 → 媒体类型）→ spine（阅读顺序）；目录优先 EPUB3 nav.xhtml，回退 NCX。
  • XHTML → Block 清洗：标签白名单（p / h1–h6 / img / blockquote…），CSS 只取影响排版的最小集（字号/行距/缩进/对齐），图片转成资源引用。
  • DRM 加密的书明确报 UnsupportedFormat，不静默降级。

TXT 解析细节

  • 编码三级判定：BOM → UTF-8 合法性校验 → chardetng 采样（GB18030/GBK/Big5…），结论全书复用。
  • 流式分章：只扫每行行首 N 个字符跑分章状态机（「第X章 / Chapter N / 卷…」），记字节偏移不复制文本；没有任何章节标记的巨书按固定字数切逻辑块。
  • 大文件友好：200MB 的 TXT 全程 mmap，内存占用与书的大小无关。

四一次开书的调用链（Flutter API 视角）

宿主只需要依赖 rrk_reader 包，调用一条线：openBook → toc → loadChapter / pagesOf → renderPage。所有重活在 Rust 线程池，Dart 侧只见 Future / Stream，UI 线程零等待。

图 4 · 一次开书的调用链与性能预算

// 最小接入：三步开一本书
final engine = await RrkEngine.create();
final book = await engine.openBook('/path/to/book.epub');

final toc = await book.toc();                                  // 目录
final pages = await book.pagesOf(chapterId, style, viewport);   // 分页
final page = await book.renderPage(PageRef(pages.first));       // 渲染指定页面
// page.geometry → Flutter 自绘；page.rgba → 直接贴图

五缓存：为什么第二次打开是瞬时的

排版结果是不可变对象，因此可缓存、可落盘 —— 这是 Rust 内核最持久的收益（Flutter 原生排版结果不可序列化，关掉就没了）。缓存 key 由三要素组成，改字号只失效布局、转屏只排可见页：

图 5 · 三级缓存：内存快、磁盘免重算、源数据常驻

性能纪律速览

  • 关键路径零全量：整本书的解压 / 分章 / 排版永远不出现在开书的关键路径上。
  • 一次 FFI = 一个任务：绝不逐行跨界；首帧路径 FFI 往返 ≤ 2 次，大块数据零拷贝。
  • 永远有可显示的东西：快照 → 估算页 → 精排页三级交付，替换时按语义坐标重锚、不跳动。
  • 全自研、代码可控：解析 / 解压 / 排版 / 渲染管线全部自研，无黑盒 SDK；第三方仅限纯 Rust 可审计白名单件。
